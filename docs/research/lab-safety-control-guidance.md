# Lab Safety Control Guidance

**Purpose:** Define testable safety requirements for intentionally vulnerable authentication and protocol labs before a runtime is selected. This is design research, not evidence that the current product implements these controls.

**Source status:** The sources below are authoritative guidance and product documentation, not regulations that automatically bind this project. “Source guidance” summarizes what a source recommends or describes. “Project recommendation” translates the threat model into acceptance criteria. The project has selected synthetic scenario-owned targets only and zero durable trace retention by default; runtime, deployment model, jurisdiction, and any future exception remain open.

## Source-backed guidance

- **Isolation is layered and containers are not equivalent to VMs.** NIST describes namespace isolation for filesystems, networking, IPC, hostnames, user information, and processes; resource allocation limits; and filesystem virtualization. It also warns that containers share a kernel and provide a weaker boundary than VMs, and that network defaults may permit container-to-container and host traffic. [NIST SP 800-190, §§2.3, 3.3.3, 3.4.2](https://doi.org/10.6028/NIST.SP.800-190)
- **Constrain outbound network paths.** OWASP recommends network-layer restrictions so an application can reach only legitimate routes where the destinations are known; it cautions that URL filtering is difficult and deny lists are bypass-prone. [OWASP SSRF Prevention Cheat Sheet, network layer and deny-list sections](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html). Docker documents `--network none` as an option that leaves only loopback in a container. [Docker: None network driver](https://docs.docker.com/engine/network/drivers/none)
- **Limit filesystem exposure.** Docker warns that bind mounts expose host paths and are writable by default; read-only mounts can prevent writes. [Docker: Bind mounts](https://docs.docker.com/engine/storage/bind-mounts/). NIST recommends read-only container root filesystems and bounded write locations. [NIST SP 800-190, §4.4.4](https://doi.org/10.6028/NIST.SP.800-190)
- **Run with least privilege and bounded resources.** NIST recommends non-privileged image users and resource isolation. [NIST SP 800-190, §§2.3, 4.1.2](https://doi.org/10.6028/NIST.SP.800-190). Docker documents that CPU and memory are unlimited by default unless constrained, and exposes resource limits. [Docker: Runtime constraints](https://docs.docker.com/engine/containers/run/)
- **Treat orchestration access as highly privileged.** Docker warns that anyone controlling its daemon can create containers with powerful host filesystem access and says APIs that provision containers need careful parameter checking. [Docker Engine security](https://docs.docker.com/engine/security/)
- **Audit security-relevant activity without placing secrets in logs.** OWASP recommends logging security events, validating and sanitizing untrusted event data, and excluding or masking passwords, access tokens, connection strings, and cryptographic keys. [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html). NIST recommends associating container creation with individual identities and logging it for an audit trail. [NIST SP 800-190, §4.4.5](https://doi.org/10.6028/NIST.SP.800-190)
- **Define disposal and secret cleanup.** NIST says container disposal plans should address destruction, data extraction, and cryptographic-key revocation or deletion. [NIST SP 800-190, §6](https://doi.org/10.6028/NIST.SP.800-190). OWASP Secrets Management says exposed secrets need prompt revocation/deletion and secrets in logs need a removal process that preserves log integrity. [OWASP Secrets Management Cheat Sheet, §9.2](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)

## Proposed project requirements and verification

These are recommendations for the product’s safety baseline, derived from the sources above. They are deliberately runtime-neutral. Every requirement should become an automated acceptance check against the eventual deployment adapter and lab lifecycle.

| Area | Recommended acceptance requirement | Example verification |
|---|---|---|
| Default isolation | A lab starts with no route to the public internet, host services, metadata endpoints, or other labs. The only permitted network is the private scenario network needed for that exercise. A capability to reach live systems is absent by default and requires a distinct, explicit product decision and design review. | From a running lab, probe loopback, host gateway, private/link-local/metadata addresses, peer lab addresses, and public DNS/IP destinations; verify each is unreachable. Verify the lab can reach only declared scenario endpoints. Test IPv4, IPv6, DNS rebinding/redirect paths, and alternate URL schemes wherever URL-driven fetches exist. |
| Target allowlists | Scenario outbound destinations are declared by stable endpoint identity and enforced at the network boundary as well as validated at the application boundary. Do not rely on a hostname string check or deny list alone. Reject unlisted destinations and redirects that leave the scenario set. | Attempt unlisted hostnames, IP literals and encodings, DNS answers that change between validation and connection, redirects to prohibited ranges, and non-HTTP schemes. Confirm no packet leaves toward a rejected destination. |
| Filesystem boundary | A lab cannot read or modify host/project files or another lab’s data. Use no host bind mounts by default; any required fixture mount is narrow and read-only. Mutable scratch storage is private to one run and has a hard size limit. | Inspect runtime mount configuration; attempt writes to fixture and host paths; attempt traversal and symlink escape; fill scratch storage and verify the configured bound. |
| Synthetic data | Built-in fixtures use generated identities, credentials, keys, claims, and endpoints. No production credentials, personal data, or copied customer data are seeded into labs. User-supplied material is labeled untrusted and is not silently persisted. | Scan fixtures and images for known secret formats and prohibited real identifiers; verify seeded credentials are synthetic and scoped to the local scenario; inspect storage and telemetry after submitting input. |
| Resource and time bounds | Every lab run has explicit CPU, memory, process/thread, storage, output, and wall-clock ceilings. Limits are mandatory defaults, not optional hints; expiry terminates the run and dependent processes. Capacity errors fail closed without starting an unbounded process. | Execute CPU, memory, fork/process, disk, output, and long-sleep exhaustion cases; verify each limit terminates or rejects the run within an agreed bound and other product functions remain responsive. |
| Inter-scenario isolation | Each run receives a unique namespace, identity, credentials, filesystem area, network scope, and cleanup handle. A compromised scenario must not enumerate, attach to, signal, or access another scenario. Reuse only immutable, read-only artifacts. | Run concurrent labs; enumerate processes, interfaces, mounts, service discovery, and identifiers from one lab; try cross-run file, socket, credential, and control-plane access. |
| Secrets and redaction | Never inject operator/deployment secrets into intentionally vulnerable targets. Use disposable scenario credentials. Redact secrets before persistence, event logs, traces, exports, and error reporting; treat redaction as defense in depth, not permission to accept real credentials. | Submit sentinel secrets in headers, bodies, URLs, errors, and malformed inputs; search every persistent and observable sink for the sentinel. Verify scenario secret revocation/invalidation after stop, reset, timeout, and crash. |
| Audit and retention | Record attributable lifecycle events (create/start/stop/timeout/reset/cleanup), selected scenario/version, policy decisions and denials, resource-limit termination, and cleanup outcome. Do not log raw tokens, passwords, private keys, request bodies, or arbitrary user payloads by default. Define a retention period and deletion behavior before collecting persisted user content. | Verify event sequence and run identifier; ensure security logs survive a lab crash but contain no sentinel secrets; verify retention expiry deletes run data and backups according to the documented policy. |
| Reset, cleanup, and failures | Reset destroys the run’s mutable state and credentials, terminates child processes, closes listeners, detaches network/file resources, and returns the scenario to a known clean fixture state. Cleanup is idempotent and retried/reconciled after partial failure or host restart. If cleanup status is unknown, block a fresh run from reusing that run’s identifiers or resources. | Reset during normal exit, timeout, process crash, adapter failure, and host restart; verify no child process, listener, mount, network endpoint, credential, or writable state remains. Repeat reset and confirm idempotence. |
| Runtime/control plane | The lab controller exposes only fixed scenario operations; untrusted scenario input cannot select arbitrary images, mounts, privileges, host paths, runtime flags, or daemon APIs. Run targets non-root with minimum capabilities and a read-only root filesystem where supported. | Fuzz all request fields and serialized scenario definitions; assert unsupported privileged settings are rejected before runtime invocation. Audit runtime configuration for privileged mode, host namespaces, devices, and daemon socket mounts. |

## Requirement-level evidence and policy rationale

The source guidance informs the control area; it does not by itself mandate
every project choice below. Where the requirement is stricter than published
guidance, it is identified as an explicit project policy to contain hostile
scenario code and protect a solo developer's host and synthetic data.

| Requirement | Source basis | Project policy or ownership |
|---|---|---|
| LAB-01 default deny / platform-created resources | NIST SP 800-190 §§2.3, 3.3.3, 3.4.2 discusses least privilege, namespaces, and container isolation. | The project denies host/control-plane/peer access by default; only the platform can create private per-run resources. ROAD-005 owns declaration fields. |
| LAB-02 host/control-plane boundary | NIST SP 800-190 §§3.3, 3.4.2; [Docker Engine security](https://docs.docker.com/engine/security/) treats daemon control as highly privileged. | Never mount host/runtime credentials or expose management APIs to hostile scenario code. |
| LAB-03 outbound/inbound target restrictions | [OWASP SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) recommends network-layer allowlisting; NIST SP 800-190 §4.4.2 covers egress controls and §4.4.4 discusses unexpected listeners and destinations. | Only scenario-owned targets/peers are allowed; no host-published listeners or general external targets. This is a deliberate restriction; future external testing requires a separate decision. |
| LAB-04 synthetic-only identities/secrets | [OWASP Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) recommends protection, revocation, and lifecycle management for secrets. | Production credentials and user/customer data are prohibited in labs; per-run synthetic secrets are a product boundary, not a claim imposed by the source. |
| LAB-05 per-run/aggregate hard ceilings | NIST SP 800-190 §§2.3, 4.1.2; [Docker runtime constraints](https://docs.docker.com/engine/containers/run/) documents that CPU/memory need explicit constraints. | Hard caps fail closed. Numeric maxima and measurement tolerances are owned by ROAD-006. |
| LAB-06 per-run separation | NIST SP 800-190 §§3.3.3, 3.4.2 discusses namespace isolation and shared-kernel limitations. | Require separate state, identity, network, and quotas for each run; ROAD-006 must assess residual shared-kernel risk. |
| LAB-07 minimize/redact traces | [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) advises excluding/masking passwords, tokens, keys, and sensitive data; NIST SP 800-190 §4.4.5 addresses container audit. | Unknown fields are omitted by default, and unredacted synthetic values are visible only in an explicit run-scoped teaching view. |
| LAB-08 ephemeral retention/deletion | NIST SP 800-190 §6 addresses container disposal and data/key handling; OWASP Secrets Management §9.2 discusses exposed-secret cleanup. | Zero durable trace retention is the default because no persistence purpose or data policy has been selected. Persistence/export requires a new decision. |
| LAB-09 protected audit | OWASP Logging recommends recording security events while sanitizing event data; NIST SP 800-190 §4.4.5 recommends identity-associated container audit. | Audit stores lifecycle metadata but no raw protocol secrets; audit unavailability stops/refuses execution. |
| LAB-10–12 reset, cleanup, and fail-closed recovery | NIST SP 800-190 §6 discusses disposal and destruction; OWASP Secrets Management §9.2 recommends revocation/deletion after exposure. | Idempotent cleanup, restart termination, quarantine on uncertainty, and no fallback to a weaker mode are project safety decisions. ROAD-006 owns proof. |
| LAB-13 secure/vulnerable separation | `docs/architecture/product-architecture.md`, **Lab safety architecture**, and `docs/architecture/protocol-lab-architecture.md`, **Protocol module contract**, establish separation as existing project architecture. | Build/import checks and explicit labels are required before vulnerable execution; this preserves the established architecture boundary. |
| LAB-14 executable artifact integrity | NIST SP 800-190 §§4.1.2, 4.2.3 discusses trusted container images and image configuration. | Immutable identity/digest verification and rejection of unknown artifacts are release requirements; ROAD-005/006 define fields and adapter verification details. |

## Decisions and unknowns to settle in roadmap

1. **Execution boundary:** local process sandbox, OS container, VM, or a tiered model. NIST’s shared-kernel caveat means the acceptable boundary depends on threat model and deployment environment; this research does not choose one.
2. **Networking:** the current baseline permits only scenario-owned synthetic targets. Any proposal to reach external test/provider endpoints is a new product-owner decision, not an open implementation option under ROAD-004. It would require scope authorization, destination control, abuse limits, and a new threat review before implementation.
3. **Persistence:** the current default is no durable trace retention. Any later user-created scenario or captured-exchange persistence/export needs a separate purpose, location, encryption/access, TTL, export, and deletion policy before implementation.
4. **Limits:** numeric CPU, memory, process, storage, input/output, concurrency, and duration ceilings, adjusted for target host constraints and scenario needs.
5. **Audit model:** identity available in a single-developer local product, log location/integrity, events, and the acceptable retention period. Avoid collecting unnecessary personal data.
6. **Failure guarantee:** decide whether the product can promise cleanup after abrupt machine power loss or runtime failure, and how it detects/reconciles orphaned resources on restart.
7. **Verification matrix:** platform/runtime versions and automated isolation tests required before a lab is considered supported.

**Research boundary:** This artifact identifies source-backed principles and proposed test criteria. It does not claim legal compliance, complete isolation, safe public hosting, or implemented protection. Container controls alone do not prove resistance to kernel/runtime escape; if hostile users or public multi-tenancy enter scope, re-evaluate the isolation boundary before exposing labs.
