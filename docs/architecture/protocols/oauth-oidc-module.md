# OAuth/OIDC Protocol Module

## Purpose

This is the first protocol module in the Authentication Lab. It teaches the
protocol from the wire level upward: actors, messages, state transitions,
cryptographic claims, implementation decisions, failure modes, and secure
verification.

OAuth 2.0 and OpenID Connect are related but distinct. The module teaches
OAuth first, then adds OIDC identity semantics on top of the authorization
flow.

## Actors

The module models these actors explicitly:

- **Resource owner** — the user who authorizes access.
- **User agent** — the browser carrying redirects, cookies, and responses.
- **Client** — the application requesting authorization or tokens.
- **Authorization server** — authenticates the user and issues authorization
  codes and tokens.
- **Resource server** — accepts and validates access tokens.
- **OpenID Provider** — the authorization server capabilities used for OIDC,
  including discovery, UserInfo, and ID tokens.

The learner should be able to see which actor initiates every exchange and
which trust assumption makes the next message valid.

## Internal module structure

The concrete Go implementation should be organized around protocol concepts:

```text
oauthoidc/
  model/          protocol requests, responses, claims, errors
  authorize/      authorization request and consent state machine
  token/          code exchange, access tokens, refresh tokens
  oidc/           discovery, nonce, ID tokens, UserInfo
  client/         demo public/confidential clients
  resource/       protected resource and token validation
  keys/           signing keys and JWKS publication
  observe/        protocol events emitted by the module
  variants/       secure and intentionally vulnerable implementations
  exercises/      scenario definitions and verification checks
  tests/          protocol, security, and exercise tests
```

These are implementation packages behind the protocol module interface. The
Lab control plane should not import individual packages such as `token` or
`authorize` directly.

## Protocol state machines

The module should make state transitions explicit instead of hiding them in
HTTP handlers.

### OAuth authorization-code flow

```text
Unstarted
  -> AuthorizationRequested
  -> UserAuthenticated
  -> ConsentGranted
  -> CodeIssued
  -> CodeRedeemed
  -> AccessTokenIssued
```

Invalid transitions are observable outcomes:

- code reused;
- code expired;
- wrong client redeems code;
- wrong redirect URI;
- invalid PKCE verifier;
- missing or mismatched state;
- unsupported response type;
- unauthorized scope.

### OIDC flow

OIDC adds these requirements and observations:

- issuer discovery;
- authorization request with `openid` scope;
- nonce generation and validation;
- ID-token signature validation;
- issuer and audience validation;
- `iat`, `exp`, and subject claims;
- optional UserInfo request using the access token.

The module should show that an access token and an ID token have different
audiences and purposes.

## First exercise sequence

### Exercise 1: Authorization-code flow

Goal: understand the actors, redirects, authorization code, and token
exchange.

Secure behavior:

- exact redirect URI matching;
- short-lived, single-use authorization code;
- client binding;
- authorization-code exchange over a protected channel.

Evidence:

- authorization request;
- login and consent events;
- redirect containing code;
- token request;
- token response;
- code invalidation.

### Exercise 2: Public clients and PKCE

Goal: understand why a public client cannot safely keep a client secret.

Secure behavior:

- `S256` code challenge;
- verifier required at token exchange;
- verifier bound to the authorization code;
- plain PKCE rejected or explicitly labeled as weaker.

Attack: intercept a code and attempt redemption without the verifier.

### Exercise 3: State and login CSRF

Goal: understand that PKCE and state protect different properties.

Secure behavior:

- unpredictable state generated by the client;
- state stored in the client session;
- returned state compared before accepting the callback;
- failed comparison stops login completion.

Attack: inject an authorization response created for another browser session.

### Exercise 4: OIDC identity layer

Goal: distinguish OAuth delegation from authentication with OIDC.

Secure behavior:

- discovery document identifies the issuer and endpoints;
- `openid` scope is required for an ID token;
- nonce is bound to the browser session;
- ID-token issuer and audience are validated;
- signature is checked using the expected issuer's JWKS.

Attack: submit a token with a valid signature but the wrong issuer or
audience.

### Exercise 5: JWT validation

Goal: understand that decoding a JWT is not validation.

Secure behavior:

- permitted algorithm configured by policy;
- signature verified;
- issuer, audience, time, and required claims checked;
- key selected from the expected issuer's JWKS;
- algorithm confusion and unsigned-token cases rejected.

### Exercise 6: Refresh tokens and lifecycle

Goal: understand expiry, rotation, reuse detection, and revocation.

Secure behavior:

- refresh-token rotation;
- family or lineage tracking;
- reuse detection;
- access-token expiry;
- explicit revocation event;
- no raw refresh-token storage in traces.

## Secure and vulnerable variants

The secure variant is the reference behavior. Vulnerable variants are named by
the weakness they demonstrate rather than by a generic `insecure` switch:

```text
secure
missing-state
missing-pkce
weak-redirect-validation
weak-id-token-validation
refresh-token-reuse
```

Each variant must define:

- the exact behavior changed;
- the attack precondition;
- expected evidence;
- why the secure behavior prevents it;
- tests proving the variant remains isolated.

Vulnerable variants must not be imported by the secure implementation. The
build and test layout should make that dependency direction enforceable.

## Trace model

The module emits protocol-specific events that the shared observation layer
normalizes into exchanges.

```text
OAuthEvent {
  exchange_id
  scenario_id
  actor
  event_type
  method
  uri
  headers
  parameters
  claims
  security_properties[]
  outcome
}
```

Sensitive fields have explicit classifications:

- visible: protocol names, endpoint paths, scopes, claim names;
- masked: authorization codes, access tokens, refresh tokens, cookies;
- omitted: passwords, private keys, PKCE verifiers, client secrets.

The learner may inspect the shape and relationships of a secret without
receiving a reusable secret outside the scenario.

## Verification model

Verification is part of the protocol module, not a UI assertion. Every exercise
has checks at three levels:

1. **Protocol checks** — messages and state transitions follow the protocol.
2. **Security checks** — validation and failure behavior meet the exercise's
   security property.
3. **Learning checks** — the learner can identify the relevant actor, message,
   weakness, and mitigation.

Example:

```text
Check: callback_state_is_validated
Given: callback state differs from client session state
Expect: login is rejected
Observe: callback_rejected with reason state_mismatch
```

## First implementation boundary

The first implementation should include one demo client, one authorization
server/OIDC provider, one resource server, and one browser-facing flow. It
should not yet implement a generalized multi-provider federation layer.

The module should expose a small protocol-neutral result to the Lab:

```text
ExerciseResult {
  status
  exchanges
  findings[]
  verification_results[]
  learning_outcome
}
```

## Decisions currently proposed

- OAuth 2.0 authorization code is the first executable flow.
- OIDC is added after the OAuth flow is observable and testable.
- State machines are explicit and tested independently of HTTP handlers.
- Secure and vulnerable variants are separate implementations.
- Trace redaction is enforced before data reaches the UI.
- Security verification belongs to the protocol module.
- The first module uses one local demo client, provider, and resource server.
