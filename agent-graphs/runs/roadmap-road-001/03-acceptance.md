# D3 — Acceptance and risk map

**Purpose:** Define when ROAD-001's guide is usable and safe.

**Inputs:** D1 scope, D2 code map, backlog ROAD-001/002, product/security docs.

## Acceptance

1. A facilitator has a consistent opening, neutral task prompts, and debrief questions.
2. Tasks map to real current UI paths and distinguish synthetic simulation, local inspection, and non-validation boundaries.
3. The scorecard separates observed behavior, participant interpretation, moderator inference, and direct quotes.
4. Draft thresholds and interpretation rules are stated before field sessions; owner signoff is a prerequisite to recruiting.
5. The participant set and findings are described as qualitative and directional, not statistical proof.
6. The guide forbids using production credentials, real tokens, third-party systems, or live traffic and minimizes retained personal data.

## Risks and failure cases

- Leading prompts could bias the result; use open prompts and reserve hints for recovery, recording every hint.
- Current synthetic labs may be confused with real protocol behavior; directly test what participants believe each tool proves.
- A small convenience sample cannot establish market size; record this limit and avoid broad demand claims.
- A participant may paste real secrets or request a live target; stop that path and substitute only a generated example.
- Inconsistent tool familiarity or technical environment could confound completion; record prior experience and whether setup help was needed.

## Proof

Review prompts against the current components and labels, inspect guide for a pre-session decision rubric, run whitespace and relative-link checks, and confirm no code/tests changed.
